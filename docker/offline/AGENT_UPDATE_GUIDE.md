## 2. 更新前先核实

1. 查看工作区状态、项目指令与用户本次变更范围，保留他人未提交修改。
2. 获取现场当前镜像 ID/标签、部署绝对路径、启动脚本、端口映射、挂载、
   Docker 版本和沙箱镜像版本。没有现场访问能力时，由现场提供必要信息。
   不输出包含密码的完整 `docker inspect` 或环境变量列表。
3. 核对发布基线源码与目标源码，列出新增、修改、删除、重命名文件。
   不要仅对仓库 HEAD 做 diff，也不要默认现场仍是最初的 20260909。
4. 检查 Python 依赖、uv.lock、系统库、前端构建、启动参数、元数据库迁移
   和持久化数据格式是否变化。
5. 记录本次升级版本、基线镜像 ID、变更范围、验证方法、预计停机步骤及
   回退条件。使用唯一版本标签，保留旧版本，避免覆盖旧标签。

## 3. 选择交付方式

| 变更 | 优先方式 |
| --- | --- |
| 仅配置 | 提供配置差异和操作步骤，不更新镜像 |
| 仅 Python 代码，无依赖或迁移变化 | 基于现场已加载镜像制作离线代码补丁 |
| 前端页面 | 联网环境编译，发布实际静态产物，不能只复制 TS/TSX 源文件 |
| Python 依赖、系统库、Oracle 客户端、入口改变 | 联网构建并导出新的平台镜像 |
| 分析沙箱依赖改变 | 重建沙箱镜像，平台镜像是否更新按实际变更判断 |
| 数据迁移或复杂跨模块变化 | 优先完整版本包，另附迁移和数据恢复方案 |

未变化的沙箱镜像无需重复交付。补丁必须绑定明确基线，不能无限叠加；
若现场版本不一致或已叠加多次补丁，应重新制作完整版本。

## 4. 小型代码补丁制作原则

推荐交付目录：

```text
update-<version>/
  RELEASE.md          # 基线、新版本、改动、停机和回退说明
  manifest.json       # 基线镜像 ID、目标版本、文件清单与哈希
  SHA256SUMS
  Dockerfile.patch
  payload/            # 经审核的代码/静态产物，保持容器内相对目录
  upgrade.sh          # 本次实际制作并测试的升级脚本
  rollback.sh         # 本次实际制作并测试的回退脚本
```

这些是后续 Agent 要制作的产物，目前仓库没有通用补丁发布器。
不要向用户声称这些脚本已经存在。

Dockerfile 示意（实际基线标签和 ID 由本次发布确定）：

```dockerfile
ARG BASE_IMAGE=k-ics:20260909
FROM ${BASE_IMAGE}
COPY payload/ /app/
```

现场构建必须只用已加载镜像，不执行 apt、pip、uv sync、npm install 或下载。
构建前校验本地基线镜像 ID；可使用 `docker build --pull=false --network=none`。
该参数不替代离线验证：缺失基线时仍可能尝试获取元数据，应提前失败。

- 确认 Python 模块实际从 `/app/packages/...` 加载；若代码装在 site-packages
  且不是 editable 安装，单纯 COPY 不生效，应改为完整镜像或离线重装方案。
- COPY 不会删除旧文件。删除/重命名必须有经过审核的精确删除清单，并在
  新镜像构建阶段处理；不能对宿主机或挂载数据目录做宽泛删除。
- 仅复制明确列出的文件，不打包整个未清理工作目录。排除 `.env*`、
  `configs/my`、私有文档、凭据、上传文件、日志、数据库、缓存及本地虚拟环境。
- 不以 `docker cp` 到运行容器或 `docker commit` 作为正式交付方式。
- 验证新镜像中的模块来源、版本及关键改动实际生效。

## 5. 完整镜像制作原则

在联网构建服务器完成依赖解析、UV 安装、前端编译和测试，按目标 amd64
构建。核查 `docker/offline/Dockerfile`，平台目标为 `--target runtime`，
沙箱目标为 `--target sandbox`；不能漏写目标而误交付最后一个 stage。
前端产物应按当前项目构建流程生成，不默认历史静态资源是最新的。

保留构建日志、源码快照、版本和包清单。导出需要变化的镜像并生成校验值，
在无外网条件下验证 `docker load`、启动与关键功能。交付仅包含所需依赖，
不包含实际客户凭据和运行数据。

## 6. 现场升级流程

1. 校验升级包和基线版本，检查磁盘空间，先加载或构建新镜像。
2. 记录原容器和启动参数；在约定的维护窗口停止新任务，等待或处理在途任务。
3. 停止平台，备份 `data/`、`site.toml`、`site.env`、`certs/` 和启动脚本。
   SQLite/Chroma 一致性备份应在停服后进行；备份含敏感数据，留在受控位置。
4. 修改或生成本次启动脚本，使平台使用新镜像标签。
   初始 `start.sh` 的镜像检查、初始化容器和正式启动均写死 20260909，
   必须全部处理。若引入版本变量，确保脚本实际读取，不能只添加到 site.env。
5. 沙箱变更时更新 `site.env` 中 `KICS_SANDBOX_IMAGE`，确认新镜像已加载。
6. 保留原挂载、部署绝对路径、绑定 IP、端口和 Docker socket 配置，
   替换平台容器。不要同时启动两个平台写同一个 SQLite/Chroma 目录。
7. 进行验收；失败时按已准备的回退步骤处理。成功后记录实际部署版本及
   镜像 ID，保留旧镜像和备份一段约定时间。

现场持久化挂载（以实际启动配置为准）：

| 宿主部署目录 | 容器目录 |
| --- | --- |
| data/pilot | /app/pilot |
| data/logs | /app/logs |
| site.toml | /app/docker/offline/site.toml，只读 |
| certs | /app/certs，只读 |
| /var/run/docker.sock | /var/run/docker.sock |

`KICS_HOST_PILOT` 必须指向宿主的实际 data/pilot 绝对路径，不能填容器路径。
镜像中的 `/app/pilot` 会被挂载覆盖，修改该目录的初始化文件不能仅靠新镜像
COPY 生效。需要单独、可回退的数据目录迁移，不能覆盖整个现有 pilot。
同理，镜像内 site.toml 的变化不会覆盖现场挂载配置。

修改 site.env 后需重建容器，单纯 restart 不更新环境。不要将默认
127.0.0.1:5670 覆盖到现场原本的内网 IP 或自定义端口。

## 7. 验证与回退

至少验证：健康接口、首页和前端资源、实际变更功能、普通/流式模型响应、
涉及的数据库连接和查询、文件分析、Excel/图表输出及沙箱结束清理。
根据变更范围检查旧功能兼容性；不得把 mock 测试说成真实客户联调。

回退分两类：

- 无数据迁移且数据格式兼容：停止新容器，以旧镜像和旧启动配置重建，继续
  使用原数据目录，验证健康状态和业务功能。
- 有数据库/数据格式迁移：不能仅切旧镜像。执行经过验证的逆迁移，或在停服
  后恢复升级前备份再启动旧版本。恢复备份会丢失升级后的新增数据，必须在
  方案中明确并按用户授权处理。

禁止清理其他业务容器、执行全局 Docker prune、删除现场数据目录，或在
没有核实的情况下重新初始化 SQLite。保留原服务配置和业务数据。
